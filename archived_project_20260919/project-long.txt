BELT TENSION  
=======================================================================================================  

Tool: PF Makes / Diyshift GT2 Belt Tension Meter (RC2), 3D printed, 0-3 dial.  
Calibrated against the music wire to read 1.9 as instructed.  

IMPORTANT: the meter's lookup tables are for 6mm and 9mm GT2/GT3 only. A 12mm  
belt deflects less at the same tension, so the meter reads roughly 0.2 HIGH  
against the 9mm table. Use it primarily for MATCHING the two belts; treat  
absolute figures as indicative.  

Reference points:  
 Table (EPDM column) tops out at 29.4 N (6.5 lb) = reading 3.0  
 Voron A/B EPDM spec 1.9-2.3  
 2 kg (19.6 N) hung from a 12mm sample read 2.8 on this meter  
 Table value for ~20 N on 9mm EPDM is 2.6 — hence the ~0.2 offset  

SUPERSEDED 26/08/2026 — THE RC2 METER CANNOT SET TENSION ON THIS MACHINE. Its  
EPDM table tops out at 29.4 N and this gantry needs ~40 N, so the working point  
is off the top of the scale. Everything above is still valid as background on  
why the meter reads ~0.2 high on 12mm belt and why it is usable for MATCHING,  
but it cannot give the absolute figure.  

METHOD NOW: pluck the belt and measure the note. T = 4L^2 f^2 mu. The reference  
state is 85/88 Hz on a 260mm span = 37/40 N, which reads 2.8 on the RC2.  

Lever positions differ between upper and lower belt — expected, not a fault.  
Belt path lengths differ because the idler arrangement reverses between the  
motor towers and the crossbeam joint. Tension is what matters, not lever  
position.  

NOTE: the NEMA17 radial force table in the meter's manual does NOT apply to  
this machine. The M23CL motors drive through spider couplings into a separate  
shaft carried in its own upper and lower bearings (double shear), with the  
pulley between them. Motor bearings see torque only, no radial belt load. The  
limit is the 625-2RS pulley bearings and shaft bending, both with headroom.  

Belts could not be normalised by hand — the motors are too heavy to backdrive  
the gantry.  

CRITICAL, AND IT COST THREE DAYS: retensioning RACKS THE GANTRY unless it is  
physically held square. See FRAME GEOMETRY AND VIBRATION below before touching  
a tensioner.

CHAMBER INSULATION  
=======================================================================================================  

Material : 25mm PIR foam board (lambda 0.023 W/m.K), foil-faced  
Application : INSIDE the aluminium cladding, chamber-facing. Foil facer faces  
 chamber air directly.  
Insulated : Left side, right side, rear, top, bottom, return duct, and the  
 PIR portion of the front door  
Glazed : Front door vision panel only  

STATUS 13/08/2026: left and right internal panels, rear, return duct, and  
BASE all FITTED. Only the top remains.  

METHOD (revised this session): dot-and-dab with Dowsil 799 was the original  
plan but was skipped in favour of dry-fitting with mechanical retention. The  
panels carry gland penetrations, so the boards can be pulled off later and  
sealant added behind them if needed. Cut penetrations slightly oversize — PIR  
crushes and tears if a gland body is forced through a tight hole; gaps get  
taped afterwards. Tape the foil facer edges at the panel perimeter regardless,  
or convective air movement behind the board partly defeats the insulation.  
That is a foil tape job, not silicone.  

BASE — DONE 13/08/2026: PIR supported on 2x 2020 extrusions running across X, carried on  
printed ABS-GF brackets mounted 25mm below the top of the Z motor towers. PIR  
press-fitted between the rails and foil-taped to the vertical panels. No  
aluminium in the base at all. Two rails handle the span — 25mm PIR would sag  
over a full 415mm+ unsupported run, especially warm. ABS-GF is adequate because  
the brackets sit on the COLD side of the PIR and carry only insulation weight;  
temperature resistance is not the requirement, dimensional stability is.  
Check the press-fit tolerance on a test print first — PIR compresses more than  
expected and a fit that feels right cold can go slack warm. The tape is sealing,  
not retention.  

Panel stack:  
 Sides / elec bay 5mm aluminium + 25mm PIR  
 Rear / top 3mm aluminium + 25mm PIR  
 Bottom 25mm PIR only  
 Door (glazed) 6mm toughened glass, single pane, 469 x 606mm  

GLAZING (RESOLVED 03/08/2026):  
 6mm toughened glass, 469x606mm, captive on all four sides in the 3030 slot

=======================================================================================================  
SAFETY CIRCUIT — Duet -> PLC (R1)  
=======================================================================================================  

Duet OUT8 drives R1 coil directly. HIGH = relay energised = system healthy.  
Drops on any Duet stop/estop.  

- R1 NO contact -> PLC %I0.0 (DI_EStop_PLC) — 24V when relay energised  
- No SR latch in PLC — %I0.0 used directly in FC4. Duet OUT8 is the only latch.  
- config.g holds OUT8 LOW at boot, then asserts HIGH only if the stop button  
 reads healthy (sensors.gpIn[3].value = 1), with a console message either way.  
- Drops via M42 P0 S0 in sleep.g, trigger3.g.  
- OUT8 does NOT drop on M0 (end of print) — only on genuine stop/estop.  
- trigger0.g (flow switch) is deleted; that path no longer exists.

MODBUS RTU — Duet <-> PLC  
=======================================================================================================  

Physical layer : Duet 3 6HC onboard RS485. RS485_EN jumper fitted. IO1  
 dedicated — do not use IO1 for anything else.  
Cable : OSP1 1x2x24AWG overall screened, drain grounded at PLC end  
 only, 260mm run — no termination resistor needed  
Duet config : M575 P3 B9600 S7  (P2 on RRF 3.6.x)  
Protocol : 9600 8N1, Duet = master, PLC CB1241 = slave address 1  
Polling : daemon.g every 10s - RRF re-runs the file itself once end of  
 file is reached. Was 5s; the figure was changed and this line  
 lagged it until 29/08/2026. M260.1 write of all 5 registers in one  
 transaction, then M261.1 read. The M261.1 call is INLINED in  
 daemon.g, not called via M98 — DSF 3.7.0-beta.1 fails to  
 declare a new local var inside a file invoked via M98 from  
 within an active while loop.  
Note : RRF 3.6.x has NO bitwise operators — use mod arithmetic for  
 bit extraction  
NOTE : RRF 3.7.0 changed M575 port numbering — P2 became P3. Applied on  
 20/08/2026 when upgrading to 3.7.0-beta.3: config.g and daemon.g  
 now use P3. Channel 3 reports as Aux 1 with Tx/!Rx port rs485.tx.  
NOTE : RRF 3.7.0-beta.3 — a FAILED M261.1 still declares its V variable  
 (as null) and does not clean it up on the error path. Every  
 later iteration of the while loop then fails with "variable  
 'plcRegs' already exists" and the read NEVER recovers, even once  
 the PLC answers again. Nesting the read in its own code block  
 does NOT help — only a fresh run of the file clears the scope.  
 Fix: guard before the read in daemon.g —  
   if { exists(var.plcRegs) }  
       break  
 which ends the file and lets RRF relaunch it with a clean scope.  
 Cost during an outage: read retried every ~16s instead of 5s  
 (5s G4 + ~10s relaunch delay). Verified 20/08/2026 by pulling  
 the RS485 cable — zero 'already exists', reads resumed on

FUSE RATING — 5A, NOT 3A (settled, do not revisit):  
 - Each M23CL has its own internal V_IN fuse (0157002.DRT, 2A Slo-Blo). That  
 is the device protection; a genuine motor fault clears internally first.  
 - The TDB fuse protects the cable and the JST VH output, itself rated 5A.  
 Fusing below the protected item gains nothing.  
 - 3A sits too close to real draw. Quiescent is ~0.16A/motor at 48V, but  
 accelerating AWD load adds ~0.8-1A each, higher on transients. A 3A blade  
 fuse derates above ~70% in a warm bay — nuisance blows were being designed  
 in.  
 - 4x5A = 20A matches the TDB input connector rating exactly.

KEY LEARNINGS & PRINCIPLES  
=======================================================================================================  

VERIFICATION  
- project.txt is authoritative over memory and summaries. Re-fetch before  
 producing output; never regenerate a full file from degraded context.  
- Verify against the physical part or the manufacturer's datasheet. This  
 session alone that caught: the pump being a Vario not a PWM unit; M569 D3  
 meaning stealthChop not assisted open loop; the CPAP hose OD being 17-18mm  
 not 15mm; the X beam being 3mm wall not 2mm; the FR4 not actually having  
 arrived. Forum convention and prior AI output are not evidence.  
- When a documented value and a physical observation disagree, the physical  
 observation wins. The Mellow left-rear pulley question was settled by looking  
 down the belt line, not by arithmetic.  
- Settle design questions to a firm decision before writing code or config.  

FIRMWARE  
- M569 D-parameter: 2=spreadCycle, 3=stealthChop, 4=closed loop, 5=assisted  
 open loop.  
- M569.1 must precede M569 D for a given driver.  
- M569.7 (not M569.2) is the brake control command in RRF 3.3+. All three Z  
 brakes run off one output (OUT1) — no fault isolation benefit justifies  
 splitting them.  
- vars.g requires exists() guards on all global declarations.  
- RRF 3.6.x has no bitwise operators — use mod arithmetic.  
- RRF 3.7.0: M575 P2 becomes P3. Done 20/08/2026 in config.g and daemon.g;  
 plc_read.g was already P3 (superseded, inlined in daemon.g).  
- RRF 3.7.0: a failed M261.1 leaks its V variable, poisoning every later  
 iteration of a while loop permanently, and DSF escalates the resulting  
 expression error to a full EMERGENCY STOP. exists() guards were tried and  
 do NOT prevent it. The fix is a loop block that runs ONCE per invocation -  
 see DAEMON.G SINGLE-PASS LOOP at the end of this file.  
- daemon.g must be renamed to be edited while RRF is running.  
- G1 moves without an H parameter default to H0, which applies axis limits and  
 refuses unhomed axes. Homing back-off moves need H2.  
- On CoreXY, home axes SEQUENTIALLY. A combined G1 H1 X.. Y.. keeps both motors  
 driving after the first endstop triggers.  
- M106 accepts a sensor LIST on H and uses the highest reading — a dual-load  
 fan needs no daemon.g override.  
- Brake configurations must be bench-tested in isolation (motors decoupled,  
 timing verified) before live reload under load. The Z brake spring damage  
 incident established this as a hard rule.  
- New safety-critical config.g sequences are unverified until hardware-  
 confirmed.  
- ALPS probe: enable is active high; value ceiling is 1000, so any G31 trigger  
 above that never fires.  

ELECTRONICS  
- DC 0V is WHITE H07V-K; blue is reserved for AC neutral only (BS 7671), with  
 sleeve as the sole identification and no heatshrink bands.  
- Drive base64 file content must be decoded before parsing; anchor searches by  
 unique string content, not line numbers.  
- AVIF images need `ffmpeg -y -i input.avif output.png` before viewing.  

MECHANICAL  
- M23CL-76-2804 rotor inertia dominates system dynamics. Beam mass, motor count  
 comparisons and CF vs aluminium debates are SETTLED. Do not reopen.  
- Acceleration ceiling is governed by frame resonance, not motor torque.  
 ~35,000 mm/s^2 design target.  
- 9mm->12mm conversion: each position sheds 2mm shim (22mm pulley vs 20mm  
 placeholder). Shim stacks confirmed per corner. Do not recalculate without  
 new physical evidence.  
- Mellow's left-rear documentation error is CLOSED — documentation, not build.  
- Single MGN9 rail on 20x20x3mm aluminium tube is the settled X beam config.  
- 1.3mm gaskets in the Mellow packs are 9mm-configuration parts with no place  
 in a 12mm build. Visually identical to 1mm — measure with calipers.  
- Toothed idler = upper belt path at motor towers, smooth = lower. Reverses at  
 the crossbeam XY joint.  
- Belt tooth-count parity between the two loops is irrelevant. Matched tension  
 is what matters.  

BED & GRANITE  
- Slab is volcanic rock; JB Weld 37901 for inserts, Dowsil 736 for brackets and  
 mat.  
- Insert holes are 5mm waterjet THROUGH-holes, filled with JB Weld before RTV  
 bracket bonding.  
- PIR goes INSIDE the aluminium cladding, chamber-facing. Standard foil tape and  
 standard silicone are adequate; high-temp alternatives rejected.  
- FR4: 5mm was considered, 4mm chosen and ordered. M3 bolts 1mm longer; Z max  
 reduces 1mm; sacrificial ply backing when drilling.

FRAME GEOMETRY AND VIBRATION — RESOLVED 23-26/08/2026  
=======================================================================================================  

Three days of measurement that ended with one procedure change worth more than  
everything else combined. The wrong turns are recorded deliberately: each one  
looked convincing at the time and would otherwise be repeated.  

--- What was actually wrong, in the order it was found -------------------------  

1. REAR-RIGHT Y RAIL SAT LOW. The one genuinely shimmable fault. Measured as the  
   front-to-rear change in rail differential, which is what a shim corrects:  
   0.344mm cold 23C, 0.372mm at 45C, 0.358mm at 60C — temperature independent to  
   +/-0.02mm across 23K, so it is measured COLD. Corrected with 0.5mm at the rear  
   fastener. Confirmed by two independent methods:  
      static   cold 4x4 mesh corner twist   0.283mm -> 0.011mm (repeat 0.024mm)  
      dynamic  127Hz band at X=390          2.25x rear-louder -> 0.63x rear-quieter  
      aX cross-axis coupling                1.76x -> 1.08x (near parity)  
   A 7x7 cold map then gave corner twist -0.005mm and deviation 0.067mm, the best  
   the machine has produced. PERMANENT SHIM FITTED 29/08/2026 at the same ~0.5mm,  
   replacing the slip gauge, with ALL rail fasteners torqued to 0.5 N.m - the  
   documented repeatable spec this investigation always lacked. The confirming  
   cold 7x7 re-mesh is still to be taken, and must be taken at that same torque.  

2. BELTS WERE FAR TOO SLACK. Running ~20 N against a calculated ~53 N requirement  
   (3kg gantry, 35 m/s^2) — below even the no-slack minimum of 26 N. This was  
   invisible because the RC2 meter tops out at 29.4 N, so it reads "fine" at the  
   top of its scale while the belt is half the tension it needs.  

3. THE GANTRY WAS RACKED, AND WE CREATED IT. The machine was square when built.  
   The rack appeared alongside the belt removal and retensioning, because both  
   retensioning and slackening the motor couplings move the gantry while nothing  
   holds it square. Squaring it took belt_check peak effort from 227/240 to  
   140/148, then 133/134 after tensioning — about 35% of motor authority  
   recovered in a single step.  

--- Why the rack hid for so long ----------------------------------------------  

THE MESH IS BLIND TO IT. A rack is an XY squareness error. Twist read +0.001mm,  
essentially perfect, with the gantry badly out of square. No bed measurement of  
any kind will find this.  

IT MASQUERADES AS SLACK BELTS. Raising tension 42 -> 64 N, a 52% increase, moved  
peak motor effort not at all: 238.6 -> 239.6. Hours went into tensioning belts to  
fix what was a geometry fault.  

HIGH TENSION MASKS IT. At 78 N the vibration numbers were the best ever recorded  
(8.4um mean displacement) while the motors sat at 89-94% authority. Both are the  
same finding: belt stiffness holding a racked gantry rigidly buys quiet at the  
cost of nearly all the control range. That "best state ever" was compensated,  
not healthy.  

--- The wrong turns, and why each was wrong ------------------------------------  

"IT IS A TORQUE SPEC." Tested every clamp state from original through 1.0 N.m,  
"by feel" twice, fully slack and totally loose. Vibration fell MONOTONICALLY to  
zero clamp force, with no sweet spot, and "by feel" was unreproducible (0.215 vs  
0.310 rms at X=10 from an identical procedure). There is no torque that both  
locates the rail and avoids stressing it, because clamping a straight rail  
against an untrue surface twists the carriage. Torque was never causal — it was  
only how hard the twist got squeezed. A 2.0 N.m-floor ratchet was bought for this  
plan and is the wrong tool; 1.0 N.m was tested directly and was far too tight.  

BUT A SPEC IS STILL REQUIRED, and this is the distinction that took three days to  
see. Torque is not the CAUSE, so no torque value fixes the geometry — that is what  
the shim is for. Torque is still a VARIABLE, because clamping state moves the twist  
by tens of microns, so it has to be held constant or no two measurements compare.  
Settled 29/08/2026: ALL RAILS AT 0.5 N.m, set with a torque screwdriver. Light  
enough to locate the rail without squeezing it, and repeatable, which "by feel"  
never was.  

"A BRINELLED RAIL." A burst appeared position-locked to the accelerometer sample  
(457/457/457 at X=10, 473/473/473 at X=390, ~0.16mm repeatability), immune to  
clamping state, with no ball-recirculation periodicity. Every one of those is  
equally consistent with debris, and it was neither — see below. THE LESSON: if a  
defect looks mechanical and permanent, re-test after a few hundred passes before  
spending money. Rails and blocks are FINE. Do not order replacements.  

"IT WAS DEBRIS THAT GOT CRUSHED OUT." Also wrong. Debris does not vanish and then  
return, and it cannot appear in X-only travel at a fixed X. The apparent  
disappearance came immediately after the rails were loosened, re-centred and  
re-torqued, which changes belt path geometry and therefore tension. Dropping to  
1.9 on the meter brought it straight back.  

"THE MACHINE IS 35% WORSE THAN BENCHMARK." An artefact of the metric. Acceleration  
rms weights harmless 200Hz content the same as damaging 40Hz content. Converted to  
displacement the gap did not exist. ALWAYS COMPARE IN DISPLACEMENT: d = a*9.81/(2*pi*f)^2.  

--- Procedures that came out of it --------------------------------------------  

BELT TENSION — pluck, do not meter. T = 4L^2 f^2 mu. Reference state is 85/88 Hz  
on a 260mm span = 37/40 N, which happens to read 2.8 on the RC2. ~40 N is enough;  
the earlier 53-78 N figures were sized for a racked gantry and are too high.  

TENSIONING — the tensioners are on the FRONT towers only and each pair is a  
diagonal (X = 70 back-right + 71 front-left; Y = 72 front-right + 73 back-left),  
so tensioning changes belt length BETWEEN a pair and forces a phase offset. Hold  
the gantry square against a fixture, slacken the couplings on 71 and 73 (both  
left, one per pair), tension with those pulleys free, then clamp. One operation,  
one position, and no resync needed afterwards.  

COUPLING RESYNC — the four closed-loop motors fight each other at standstill after  
any belt refit, burning 366 units of PID authority against a healthy ~70. It is a  
reassembly artefact and it RECURS, introduced by clamping the belt with the paired  
motors at whatever phase they happen to sit at.  
  - SQUARE THE GANTRY FIRST. The resync makes each motor's zero agree with wherever  
    the gantry currently is, so doing it racked makes the skew the reference. That  
    is why the fight kept "returning": 366 -> 64 -> 16, each resync re-baselining  
    onto a worse skew. LOW IDLE PID IS NOT A GEOMETRY CHECK.  
  - Motors ENGAGED AND HOLDING, slacken one coupling at a time on the plain motor  
    shaft, let the controller drive its own error to zero, re-clamp. Do NOT disable  
    the motors to re-clamp — that locks in the mechanical rest position and the  
    fight comes straight back.  

MEASUREMENT — check belt tension before any vibration comparison. is_diag.g  
isolates one belt pair at a time and is directly exposed to a tension imbalance:  
an UNCHANGED machine gave 1.03x / 1.19x / 1.02x purely from slack belts, and that  
artefact was read as a rail asymmetry for most of a day. is_xpos.g drives both  
pairs together and is largely immune.  

--- Reference state, square ----------------------------------------------------  

Plucked 85/88 Hz = 37/40 N, RC2 2.8, belt_check 133.4/133.9, standstill 70,  
silent. Mean displacement 8.4um across X, uniform 7.4-9.5 (was 7.6-14.2); X390,  
always the worst corner, went 14.2 -> 9.4. Shaper F147 — the only genuine  
isolated resonance on the squared machine is 146.9 Hz. The old F127 was derived  
on the slack, racked, preloaded machine.  

Other geometry terms, for context: the X beam bows -11.7um/K, linear, and is NOT

THERMAL BEHAVIOUR OF THE Z DATUM - METHOD AND RAW DATA, 29/08/2026  
=======================================================================================================  
Summary and the operational rules are in project.txt THERMAL BEHAVIOUR. This is  
the method and where the raw data lives.  

METHOD. Repeated G30 S-1 at bed centre, one sample every ~34s, with the hotend  
held at 150C throughout so nozzle growth is constant and excluded. Each cycle  
was batched as G30 S-1 / M400 / G1 Z10 F1000 / M400 / read, so the bed is moved  
AWAY immediately after every probe - a hot nozzle must not be left parked at  
trigger height over one spot, it locally heats the slab and corrupts the very  
thing being measured. G30 S-1 reports the RAW trigger height, which is what  
makes it usable as a repeated measurement without disturbing the datum.  

RESULT. 10.7 um per degC of chamber, R^2 = 0.93 over 39.9 -> 60.0C. 307um of  
total datum movement during the climb; 23um band and 1.2 um/min residual once  
the chamber held setpoint. Hotend varied by 0.24C across the whole run.  

FIRST ATTEMPT WAS WRONG AND IS WORTH REMEMBERING. The first logger sampled the  
probe's RESTING value (sensors.probes[0].value) against temperature, expecting  
a baseline drift toward the G31 threshold. It read exactly 0 at every sample  
from 25C to 48.5C, because a strain gauge reads zero at rest by definition -  
there is no force on it until the nozzle touches. The measurement that matters  
is the TRIGGER HEIGHT, not the resting value. That null result is kept as  
probe_thermal_20260829.csv.

WHAT IS RULED OUT:

   The G4 P800/P1500 dwells in the home macros were added 22/08/2026 assuming a
   slow solenoid. Raising them is a dead end. Trev: "its not a timing issue as
   the fail to release and stay locked subsequently".
 - NOT config.g failing to reach M569.7. config.g completed on every run - the
   M307 warning further down the file is logged every time.
 - NOT RRF's brake-control logic. Driving the port manually with M950+M42,
   completely bypassing M569.7, is intermittent in the same way. Trev: "i know
   it can work it just doesnt always".

WHAT IS LEFT: everything downstream of the command - the OUT1 output stage, the
wiring, the connector, or the coils.

PRIME SUSPECT - the commoning point. From project-long.txt LOW block:
   T1  Z brake +    Duet OUT1 signal  (all three brakes commoned)
   T2  Z brake GND  Duet OUT1 GND
All three brakes share ONE terminal pair. Three coils do not fail together, but
one shared crimp does - and that explains total silence rather than a partial
release, plus the latch-until-disturbed behaviour and the spontaneous recovery.

SECOND SUSPECT - no flyback diode. M569.7 docs: OUT/FAN pins on Duet 3 have
flyback diodes, but if a HEATER output is used "you must add a flyback diode in
parallel with the brake solenoid". OUT1 is heater-class on the 6HC (same class
as OUT0 hotend and OUT7 bed SSR). Three inductive coils switched hard with no
diode, every enable/disable cycle for months, degrades before it fails outright.

DAEMON.G SINGLE-PASS LOOP - THE "while { iterations < 1 }" FIX, 29/08/2026
=======================================================================================================  
daemon.g opens with "while { iterations < 1 }" - a loop block that executes
exactly ONCE per invocation. THIS IS DELIBERATE AND IT IS NOT A MISTAKE FOR
"while true". Do not "fix" it. Full bug report, with three separate defects
written up for Duet3D, is at /home/trev/duet_bug_report_20260829.txt.

WHY THERE IS A LOOP BLOCK AT ALL
M261.1's V parameter declares a LOCAL variable, and DSF refuses that at file top
level, logging "Cannot add local variable because there is no open code block".
The declaration silently does not happen, execution continues, and the reads
that follow fail - so the macro half-works. The PLC heartbeat kept incrementing
(M260.1 declares nothing) while the read values silently froze. A loop block
gives M261.1 the open block it needs.

An "if" block is NOT an acceptable substitute. Tested 29/08/2026: reading
plcRegs from inside one throws "unknown variable 'plcRegs^'" - a corrupted name
carrying a caret that appears nowhere in the file.

WHY IT RUNS ONLY ONCE
RRF re-runs daemon.g by itself once end-of-file is reached, so the file needs no
loop of its own to keep polling. The single-pass block gives the reads the same
shape they always had, but the SCOPE CLOSES at the end of every invocation
instead of persisting across polls.

That persistence was the fault. A failed M261.1 left plcRegs broken inside a
scope that never ended, so the loop could never recover: later iterations failed
either with "plcRegs already exists" or with "unknown variable".

WHY IT MATTERED - IT EMERGENCY-STOPPED THE MACHINE, TWICE
DSF escalates that expression error to a full EMERGENCY STOP. The machine halts,
all four CAN expansion boards drop off the bus (70-73), and M999 is required to
recover. It fired at 23/08/2026 21:41 and again at 29/08/2026 14:54:38 - BOTH
TIMES WITH THE MACHINE IDLE. No job running, no operator action.

What makes it dangerous is WHERE the expression fails. Failing while DSF is
EXECUTING a code logs an error and carries on. Failing while DSF is READING
AHEAD in the macro is what raises the Emergency Stop. That is defect 2 in the
bug report and it is the serious one.

EXISTS() GUARDS DO NOT PREVENT IT
They were tried and they do not work. Earlier notes in both project files
claimed daemon.g "carries an exists()/break guard to recover" - that was WRONG,
corrected 29/08/2026. There is no such guard and there never was one that
helped; the only exists() in the file guards vars.g loading, not plcRegs. The
single-pass scope is the entire fix.

UPSTREAM FIX EXISTS - Duet3D commit 363e8743, checked 01/09/2026
"Fixed tracking of local variables from M260.1/M261.1" (KeywordHandler.cs,
MCodeHandler.cs, CodeBlock.cs, CodeFile.cs). It fixes the top-level declaration
defect AND the leak that caused our two emergency stops: failed M260.1/M261.1
no longer register result variables, and leftovers are deleted before the
firmware declares new ones.

BUT KEEP THIS WORKAROUND ANYWAY. The commit removes the trigger, not the
amplifier - it says nothing about an expression error during READ-AHEAD
escalating to a full emergency stop, which was the HIGH severity defect in
/home/trev/duet_bug_report_20260829.txt section 4 and remains open. The
single-pass loop costs nothing and closes the scope on every invocation
whatever fails inside it. Do NOT revert to a top-level M261.1 or a persistent
loop just because the declaration bug is fixed upstream.
We ran DSF 3.7.0-beta.3 when this was written. On 08/09/2026 we upgraded to
3.7.0-rc.1, which CONTAINS the commit - confirmed by ancestry (behind_by 0)
and by the rc.1 release notes, which list all three bug fixes verbatim. The
workaround stays regardless, for the reason given above. Full mapping of the
commit onto our three reported defects is in section 13 of the bug report.

EDITING IT
daemon.g cannot be edited in place while RRF is running it - rename it (e.g.
daem6on.g), edit, rename back. To reload it without resetting the board, use
"sudo systemctl restart duetcontrolserver"; that is lighter than M999 when a
macro is all you need reloaded.
